# 归档引用生命周期与排队取消修复

最终回归复现两处问题：源人物删除后SQLite复用整数ID，旧的多态归档引用可能读取新人物；项目导入在排队阶段取消，任务池在调用业务函数前结束，批次可能仍停在queued。

删除正常资料前，在同一事务将归档entity_id变为该引用独有的负数墓碑，保留标题、收藏、标签和备注，不再跟随新对象。覆盖素材、人物、条目、笔记、作品、关系；人物删除级联关系及世界观删除级联条目的跨世界引用也提前失效。旧引用兼容读取增加创建时间检查，较晚创建的同ID记录不读取；搜索同样排除。失效界面隐藏原资料/版本链接，明确显示保留偏好、未关联新对象。

不新增表、不重置或批量迁移历史资料；既有客户端应检查missing_record，负数entity_id仅表示失效引用，不是真实实体ID。正常API删除受事务保护；绕过应用的直接SQL修改不是完整支持流程，创建时间仅为旧数据保守兜底，不是新的授权体系。重新导入同来源但原记录已失效时拒绝自动继承，需明确移除旧引用后重新确认。

导入详情/列表及恢复前，将异常活跃状态与持久任务终态对齐。排队取消能直接恢复，已提交文件仍跳过；不需要重启、不自动重发AI。

最终集成候选188后端测试与生产构建通过。新增3项覆盖ID复用、外世界正文不泄漏/偏好不继承、关系级联、旧直接SQL删除兼容及排队取消恢复。浏览器生成样本实际验证旧档案失效、原偏好保留、新正文不出现、无原资料链接；截图仅生成内容。取消测试为进程内有界队列，不是实际断电。

每次正常删除多执行归档索引UPDATE；分页详情与搜索增加时间条件，不引入后台扫描、媒体副本或新依赖。大型删除批次/RSS性能尚待，未用小样本宣称大库验收。第三方模型与原创资料未提交，原件未改写。
